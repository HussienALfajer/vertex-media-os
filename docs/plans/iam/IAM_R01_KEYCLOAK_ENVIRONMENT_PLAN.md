## 1. Objective

Give Vertex OS a reproducible, version-pinned Keycloak 26.7.4 for local development and tests. Commit the Vertex realm as reviewable configuration that contains no secrets. Prove against a real Keycloak that the realm enforces the security contract of `docs/modules/iam.md` Sections 7, 8 and 37: separate `vertex-web` and `vertex-provisioner` clients, exact redirect and logout URIs, user-profile restrictions, and the password, Argon2id, MFA, brute-force, event and session policy. Later IAM stages (MP-04 provisioning, MP-06 OIDC) build on the reusable Testcontainers harness this run delivers. The run also closes the boundary-lint residuals carried forward to this stage.

## 2. Scope

**In scope**

- Keycloak service in `infra/compose.yaml`: pinned by tag and digest, loopback-only, development mode, persistent volume, deterministic health check.
- `infra/keycloak/`: the realm import file and the non-secret server options shared by Compose and the test harness.
- Generated local secrets in `pnpm env:setup`, and `.env.example` entries. Existing `.env` files receive the missing entries without losing their current values.
- The Keycloak test harness (`apps/api/test-support/keycloak.ts`). Static configuration tests and real-Keycloak integration tests in `apps/api`.
- Boundary-lint changes for A-02, A2-02 and A2-03, with `lint:boundaries` cases.
- README (setup, URLs, reset behaviour) and the Master Plan status updates.

**Out of scope**

- Admin REST adapter, identity reconciliation, invitation dispatch, SMTP and a local mail sink (IAM-MP-04).
- Typed API configuration for Keycloak values (D-11), OIDC login, callback, sessions and back-channel logout handling (IAM-MP-05/06).
- Production realm, hostname, TLS, database and deployment design.
- WebAuthn/passkeys and a compromised-password list (D-08, D-06).

## 4. Decisions

- **D-01 Image pinning.** `quay.io/keycloak/keycloak:26.7.4@sha256:82a77884f3af238beab1e7afd63b5f530e1b5c0590bd7aa60b40a40463e29b2c` (the digest `docker pull` reported on 2026-09-23). Compose and the harness use this one reference, and a unit test fails if they differ.
- **D-02 Local runtime.** `start-dev` with the embedded dev-file database in a named volume `keycloak-data`. `pnpm infra:reset` removes it together with `postgres-data`, so IAM rows and Keycloak identities are always reset together. The realm is imported with `--import-realm` only while it does not exist. A changed realm file therefore needs `pnpm infra:reset`; the README says so. Development mode is local and test only (spec Section 38).
- **D-03 Exposure.** HTTP is published only on `127.0.0.1:${KEYCLOAK_PORT:-8080}`. The management port (9000, health) is not published; the Compose health check calls it inside the container. `KC_HOSTNAME=http://127.0.0.1:${KEYCLOAK_PORT}` makes the local issuer deterministic.
- **D-04 Realm as code with environment placeholders.** `infra/keycloak/import/vertex-realm.json` is the only source of realm policy. Client secrets and the environment-specific URIs are Keycloak import placeholders (`${NAME}`, verified against 26.7.4), supplied from `.env` by Compose and generated by the harness in tests. The committed file holds no secret and no default for one.
- **D-05 Client separation.** `vertex-web`: confidential, standard flow only, PKCE `S256` required, no implicit or direct-access grants, no service account, no device, CIBA or token-exchange grants, back-channel logout with session required and front-channel logout off. It has exactly one redirect URI, one post-logout redirect URI and one back-channel logout URL per environment. It carries no client roles, does not allow full scope, and has default scopes `basic acr profile email` with no optional scopes, so there is no `offline_access`. `vertex-provisioner`: confidential, service account only, and every interactive flow off.
- **D-06 Password policy.** `length(15) and maxLength(128) and notUsername and notEmail and hashAlgorithm(argon2) and hashIterations(2)`. There are no composition rules and no forced rotation. A compromised-password list (SECURITY Section 8, SHOULD) needs a server-side blacklist file, so it is deferred to production deployment design.
- **D-07 Argon2id.** Argon2id version 1.3, memory 19456 KiB, 2 iterations, parallelism 1 (the first OWASP Password Storage configuration). Memory, parallelism and type are server options in `infra/keycloak/keycloak.env`; iterations are in the realm policy. A test reads the stored credential to prove them. Production benchmarking stays a pre-launch task (SECURITY Section 8).
- **D-08 MFA.** The realm browser flow `vertex browser` requires the OTP form after username and password. A user without TOTP must enrol before a code is issued. TOTP policy: SHA1, 6 digits, 30 s period, look-around 1, codes not reusable. WebAuthn/passkeys (SHOULD) are deferred to production deployment design.
- **D-09 Brute force.** Protection on, strategy `MULTIPLE`, 5 failures, temporary lockout of 60 s increasing to at most 900 s, failure window 12 h, quick-login check 1000 ms with a 60 s wait. There is no permanent lockout, so an attacker cannot lock accounts for good.
- **D-10 Events and sessions.** User and admin events are on, with the default saved event types and 90-day expiry. Admin event representations are off: operation, resource and actor are kept, but no user payloads are stored. Keycloak SSO idle is 1800 s and maximum 36000 s (within SECURITY Section 11); access tokens last 300 s; refresh tokens rotate (revoke on use, reuse 0); remember-me is off. Registration and self-service password reset are off; verify-email is on. *Revised after in-run review (S-01):* the plan first turned forgot-password on. The built-in reset flow lets whoever holds the mailbox enrol a new TOTP and set a new password, so email alone would replace both factors. That contradicts SECURITY Sections 9–10 and spec Section 8. Self-service recovery returns in IAM-MP-04, with SMTP, as a reset flow that demands the existing OTP. The admin action-token lifespan is 43200 s (MP-04 may pass its own per request); the user action-token lifespan is 300 s.
- **D-11 Typed API configuration is deferred to its consumers.** Master Plan Section 13 says configuration shapes come with the stages that consume them. The API consumes no Keycloak value in this run. IAM-MP-04 maps the provisioner values and IAM-MP-05/06 the OIDC and session values into `AppConfig`. This run fixes the `.env` names those stages reuse (`KEYCLOAK_*`).
- **D-12 User profile.** The declared profile gives `username` and `email` `edit: [admin]`. `vertexUserId` gets `view: [admin]`, `edit: [admin]` and a lowercase-UUID pattern. `firstName` and `lastName` stay user-editable but not required: displayName lives in Vertex, so users are not prompted for names. Unmanaged attributes stay disabled. The Update Email required action is explicitly disabled, and `editUsernameAllowed` and `registrationEmailAsUsername` are off (spec Section 37, layers 2–3). The server feature is left at its default because layer 3 closes the route on its own.
- **D-13 Boundary lint.** `restrictedImportSyntax` rejects interpolated template dynamic imports. `node:module`/`module` is rejected in every project except `apps/web-e2e`, which uses `createRequire` legitimately. This covers every static import form through `no-restricted-imports` (the persistence adapters' overrides keep it), and dynamic, `import =` and `getBuiltinModule` routes plus any `.createRequire` member through `restrictedImportSyntax`. `restrictedRawSqlSyntax` adds bracket, template and destructuring forms. `restrictedEnvSyntax` covers:
  - `env` read through any `process` member, including `globalThis.process`, in dot, bracket or template form;
  - destructuring, including nested destructuring from `globalThis`;
  - any import, re-export or dynamic import of `node:process` in production source (none exists today).

  Aliasing (`const p = process; p.env`) and `Reflect.get` cannot be closed by syntax. They count as deliberate circumvention, which review rejects (IAM-02 Section 46A rationale).
- **D-14 Provisioner privileges.** Only `realm-management` `manage-users`. A 26.7.4 probe showed that it alone searches, reads, creates, updates, disables and logs out users, and is refused clients, events, the master realm, impersonation and granting `realm-admin` or `manage-clients`. Residual risk, recorded: `manage-users` can also reset passwords, grant `manage-users` itself, clear brute-force lockouts and read role mappings. `execute-actions-email` works, as spec Section 7.2 requires. Vertex never calls the other operations, and the secret is server-side only. Narrowing further needs fine-grained admin permissions; this is left to the Final IAM Module Audit and production review.
- **D-15 Local URIs.** Redirect `http://127.0.0.1:4200/api/auth/callback`, post-logout `http://127.0.0.1:4200/`, back-channel `http://host.docker.internal:3000/api/auth/backchannel-logout` (spec Section 25.1 paths, through the web dev origin). IAM-MP-06 proves back-channel reachability and may change these values through `.env`.
- **D-16 Harness location.** `apps/api/test-support/keycloak.ts` is the first Keycloak harness copy, next to the existing PostgreSQL one. It starts the pinned image with the committed realm and generated test secrets, and waits for management readiness and realm discovery. A shared test-support package is still decided by the IAM-02 rule.

## 5. Design notes

- **Secrets.** `pnpm env:setup` resolves named placeholders `<generated:NAME>`: each name gets its own `randomBytes(24).base64url` value, and repeated names share one. It never prints them. With an existing `.env` it appends only the keys missing from it. It refuses when a missing key shares a placeholder with a present key, or when the Docker volume that owns a newly generated secret already exists. `--force` keeps its current refusal whenever any owning volume exists. Postgres values are owned by `postgres-data`, Keycloak values by `keycloak-data`.
- **Bootstrap admin.** `KC_BOOTSTRAP_ADMIN_USERNAME` and `KC_BOOTSTRAP_ADMIN_PASSWORD` come only from `.env` (`${…:?}` in Compose, with no default). Both are generated (S-03; spec Section 38 allows no committed defaults). Keycloak applies them only when it creates the master realm, like the PostgreSQL password.
- **Built-in clients.** The realm overrides Keycloak's built-in `admin-cli` so that it has no flow at all (S-02). Otherwise it is public with direct grants on, and the built-in direct-grant flow asks for OTP only from users who already have one. No client in the realm may use the password or implicit grant; a test asserts this across all clients.
- **Failure semantics.** A missing secret stops `docker compose` before it starts anything. An unresolvable placeholder would otherwise import a literal `${…}` value. `pnpm infra:up` waits for both services' health checks, and Keycloak's check passes only after the import finishes.
- **Test fixtures.** The integration tests act through the real clients and the account REST route. To obtain a user token for the account route, the test adds a throwaway direct-grant client to the ephemeral test realm through the bootstrap admin. That client never appears in committed configuration, and production has no test path (TESTING "Identity provider in tests").

### Discoveries during the run

- **Admin authorization reads the token's roles.** With `fullScopeAllowed: false`, the first provisioner token carried no roles and every Admin API call returned 403. The realm now maps `realm-management` `manage-users` into the provisioner's scope (`clientScopeMappings`) and gives it the `roles` default scope. Its token carries exactly `resource_access.realm-management.roles = [manage-users]` and no realm roles, which the tests assert.
- **Omitted flows survive import.** A realm file that declares only the custom browser flow still gets Keycloak's built-in flows (direct grant, registration, reset credentials, clients, first broker login) bound as defaults.
- **Keycloak response shapes.** A wrong client secret returns `401 unauthorized_client`, not `invalid_client`. Logout with a registered post-logout URI and no session redirects (302) to it at once. An unregistered one gets `400` with no `Location`. After a password, the first step lands on Keycloak's own required-action page by redirect.
- **A masked test, found by mutation.** The first account-route test submitted username and email changes in one request. Once `email` was made user-editable in the realm, that test still passed, because the username refusal rejected the whole request. Each protected field is now attempted alone. A mutation run (email `edit: [admin, user]`, PKCE attribute removed) fails the account-route, profile-declaration, PKCE and client-configuration tests.
- **Server option names.** `KC_SPI_PASSWORD_HASHING__ARGON2__<OPTION>` is honoured in 26.7.4. A probe with `HASH_LENGTH=64` changed the stored `hashLength` accordingly.

## 6. Done means

1. `pnpm infra:up` on a fresh volume starts PostgreSQL and Keycloak healthy. Both publish on 127.0.0.1 only, and the `vertex` realm exists. `pnpm infra:down` keeps both volumes, and `pnpm infra:reset` removes both. PostgreSQL development behaviour is unchanged. *(MP exit: harness starts deterministically; PostgreSQL intact.)*
2. The committed realm, Compose and `.env.example` contain no credential. `pnpm env:setup` generates distinct local secrets and upgrades an existing `.env` without changing existing lines. *(MP exit: credentials absent.)*
3. Integration tests against the real pinned Keycloak prove:
   - discovery and JWKS; `vertex-web` exact redirect and post-logout matching, PKCE required, and refused implicit, password and client-credentials grants;
   - `vertex-provisioner` client-credentials access with exactly the D-14 capabilities, its refusals, and no interactive flow;
   - user-profile restrictions through the account route (username, email and `vertexUserId` unchanged; `vertexUserId` hidden), with the Update Email action disabled;
   - the password policy and Argon2id parameters, and TOTP enrolment demanded before a code is issued;
   - brute-force lockout, a LOGIN_ERROR event and an admin CREATE event attributed to the provisioner;
   - SSO and token limits, and no test secret in the Keycloak logs;
   - no client in the realm issues a token through a password or implicit grant, and self-service reset is off (added after in-run review, S-01 and S-02).

   *(MP exit: policy verifiably configured; realm reproducible without console state.)*
4. Unit tests pin the image reference across Compose and the harness, assert loopback-only ports, and assert that every client secret in the realm file is a bare placeholder.
5. `lint:boundaries` proves the A-02, A2-02 and A2-03 forms are rejected and the legitimate forms accepted.
6. The README describes setup, URLs, the realm-change reset and the secret upgrade path. The Master Plan marks IAM-MP-03 `COMPLETE` and IAM-MP-04 `READY`, with the carried-forward items attached.

## 7. Stop conditions

- A required realm policy cannot be expressed in the 26.7.4 import format without manual console steps.
- The provisioner cannot work without a role broader than `manage-users` (that is an owner decision under the spec's "documented security review").
